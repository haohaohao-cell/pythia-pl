# 预测模型为什么打不过市场：我把 0.02 的差距拆成了 0.0042 和 0.0167

我用 13 个赛季、4,630 场英超比赛训练了一个三分类模型，然后用 **3,044 场样本外比赛**去检验它。

结果它输了。log loss `0.9767`，博彩公司的收盘赔率 `0.9558`，差 **0.0209**。

这个差距本身不稀奇——模型打不过博彩市场是常态。真正的问题是：**这 0.0209 里，有多少是"我少知道了一点"，有多少是"我永远不可能知道"？**

为了回答它，我做了五个实验。四个证伪了一种"再加点特征就能追上"的幻想，最后一个把差距精确拆成了两段。

---

## 一、先说清楚：这类项目通常错在哪

如果你去搜"足球预测"，会看到大量写着"准确率 62%"的仓库。它们绝大多数栽在三件事上：

| 错误 | 后果 |
| --- | --- |
| 随机 KFold 切分 | 训练集里混进了未来的比赛，模型提前看到答案 |
| 赛后数据当赛前特征 | 比如用"本赛季场均 xG"做特征，那个数只有打完才知道 |
| 没有基准 | 只和自己比，不和任何真实报价比 |

第三条最容易被忽略，也最致命：**你在一个没有对手的考场上考 62 分，不代表你会踢球。**

所以我给这个项目立了三条硬约束：

1. **只和收盘赔率比**（去抽水后的 Pinnacle / Bet365 收盘价）
2. **walk-forward**，不用随机切分
3. **主指标 log loss**，不用准确率

---

## 二、评估框架：三件比模型重要的事

### 2.1 walk-forward

预测第 $S$ 赛季时，只允许使用 $S$ 开赛前的数据。实现上就是一个循环：

```python
for season in test_seasons:
    start = season_start(season)          # 例如 2023-07-01
    train = df[df["date"] < start]        # 只能用这之前的
    test  = df[df["season"] == season]    # 这是要预测的
    model.fit(train)
    predictions.append(model.predict(test))
```

看起来平平无奇，但它决定了整个项目是否可信。用 KFold 能把同样的模型"提升"到好看得多的数字。

### 2.2 log loss 而不是准确率

三分类的准确率几乎没有意义：一律猜主胜也能到 45%。

log loss 同时惩罚"错"和"假装确定"——你说 90% 会发生、结果没发生，罚得很重；说 45%，罚得轻。所以墙头草和莽夫都拿不了高分。

### 2.3 基准是收盘价

收盘赔率是全世界最会预测足球的人用真金白银投出来的概率，去抽水之后就是一把现成的尺子：

```python
def implied(odds):                    # odds: (n, 3) 的十进制赔率
    raw = 1.0 / odds
    return raw / raw.sum(axis=1, keepdims=True)
```

### 2.4 再加一条纪律：写防泄漏测试

上面三条都是"我打算这么做"，只有测试能保证"我真的这么做了"。

我的做法是两个 pytest：一个截断未来数据，一个**篡改未来的比赛结果**，然后断言目标比赛那一行的特征纹丝不动。

```python
def test_mutating_a_future_result_does_not_change_past_features():
    full = build(matches)
    target = matches.iloc[len(matches) // 2]

    tampered = matches.copy()
    future = tampered["date"] > target["date"]
    tampered.loc[future, ["fthg", "ftag"]] = [7, 0]     # 把未来全改成 7:0

    assert features_identical(full, build(tampered), target["match_id"])
```

这 20 行代码，比模型本身更能说明项目是不是认真做的。

## 三、模型和跑分

四个模型，从简单到复杂：常数基线、Elo + 逻辑回归、Dixon-Coles（双变量泊松 + 时间衰减）、梯度提升树；最后按前两季战绩加权融合。

| 模型 | log loss | 准确率 |
| --- | --- | --- |
| 收盘价（去抽水） | **0.9558** | 55.0% |
| 融合模型 | 0.9767 | 53.0% |
| Elo + 逻辑回归 | 0.9788 | 53.4% |
| 梯度提升树 | 0.9911 | 52.0% |
| Dixon-Coles | 0.9941 | 51.4% |
| 常数基线 | 1.0686 | 43.7% |

差距 `+0.0209`，配对 bootstrap 的 95% 区间 `[+0.0147, +0.0271]`，不含 0。

## 四、四个证伪实验

### 实验一：温度校准 —— 是不是过度自信？

给每个模型加一个温度参数 $T$：$p_i \to p_i^{1/T}$，在**上一季**的样本外预测上拟合。

| 模型 | log loss | + 温度 | 变化 | T 中位数 |
| --- | --- | --- | --- | --- |
| 融合 | 0.9767 | 0.9798 | +0.0031 | 1.00 |
| Elo | 0.9788 | 0.9805 | +0.0017 | 1.00 |
| Dixon-Coles | 0.9941 | 1.0030 | +0.0089 | 1.03 |
| 梯度提升 | 0.9911 | 0.9906 | **−0.0006** | 1.14 |

融合模型的 $T$ 稳在 1.00——它本来就没病。

更关键的是把 Brier 分数拆成「可靠性」和「分辨率」：

| | 可靠性 ↓ | 分辨率 ↑ |
| --- | --- | --- |
| 收盘价 | 0.0012 | **0.0786** |
| 融合模型 | 0.0016 | **0.0661** |

**可靠性几乎一样，差距全在分辨率。** 也就是说：模型不是不会报概率，是知道得更少。

### 实验二：xG —— 少了个关键特征？

射正是"创造机会"的粗糙代理。我接了 Understat 的逐场 xG（13 季 4,635 场，覆盖率 100%），然后做严格消融：训练窗口、测试比赛、超参数全同，唯一变量是树模型有没有看到 xG。

| 变体 | log loss | 变化 |
| --- | --- | --- |
| 梯度提升（无 xG） | 0.9911 | — |
| 梯度提升 + xG | 0.9896 | −0.0015 |
| 等权融合（无 xG） | 0.9770 | — |
| 等权融合 + xG | 0.9756 | **−0.0014** |

bootstrap：`−0.0014`，95% CI `[−0.0029, +0.0000]`，P(更好) = 0.97。方向对，但**上界正好压在 0 上**。

工程上还踩了两个坑，值得单独记：

- **赛季 ID 不是起始年**。Understat 的 2020 和 2021 都指向 2020-21，得用开球日期反推才能对上，否则整季数据静默错位。
- **队名又是另一套**。`Spurs`、`Hull City`、`Ipswich Town`、`Coventry City`——这是第三个数据源的第三套拼写。**"60% 的工作量在队名映射上"这句话，我验证了三次。**

### 实验三：伤停 —— 拿市场独有的信息

FPL 官方 API 的 `bootstrap-static` 看起来完美：669 名球员的实时状态（`a/d/i/s/u`）、出场概率、伤情说明。这一轮 **200 人**不完全可用。

然后我问了致命的问题：**能回测吗？**

不能。单个球员的 `element-summary` 接口，逐轮历史字段是：

```
minutes, starts, total_points, expected_goals, expected_assists, ...
```

**全是赛后才知道的东西，没有任何字段记录"那一轮赛前他是不是伤停"。**

API 只暴露"现在"，不暴露"当时"。没有历史快照 → 没有样本外 → 没有数字。用今天的伤停去解释过去的比赛，就是穿越。

这件事失败的原因不是技术，是**因果顺序**。

### 实验四：大小球 —— 结构模型的主场？

Dixon-Coles 产出完整比分分布，天生能定价总进球，而基于 1X2 标签的分类器不能：

```python
matrix = dc.score_matrix(home, away)                    # 10 x 10 的比分联合分布
under = sum(matrix[i, j] for i in range(10) for j in range(10) if i + j <= 2)
p_over_25 = 1 - under
```

| | log loss |
| --- | --- |
| Dixon-Coles | 0.6871 |
| 收盘价 | **0.6738** |
| 常数基准 | 0.6894 |

对庄家 `+0.0134`。但**第三行才是重点**：模型只比"每季都报同一个大球率"好 **0.0023**，而庄家比常数好 **0.0156**。

庄家在大球上有真实的分辨力，我们几乎只有水平。2023-24 最典型：实际大球率 64.7%，模型给 48.3%，庄家给 58.6%。

## 五、收尾实验：把市场当特征，权重被推到 1.0

最后一个问题：既然公开特征补不上，那**把盘口本身当特征**呢？

模型概率与去抽水**初盘**按权重混合（收盘是裁判不能用；初盘是开赛前几小时的合法信息），权重在历史赛季上调：

| | log loss |
| --- | --- |
| 模型 | 0.9767 |
| 初盘 | 0.9601 |
| 混合（调优） | 0.9608 |
| 收盘 | **0.9558** |

**优化器把权重推到了 1.00**——九季里六季完全是 1.00。

也就是说：**一旦手里有盘口，这个模型就是一个噪声项，最优用法是扔掉。**

所以"补回 76%"这个数字要读准：**是初盘自己补的，不是模型补的**。

**[图 2]** 盘口梯子

真正有用的是这条梯子：

```
收盘 0.9558  ──+0.0042──▶  初盘 0.9601  ──+0.0167──▶  模型 0.9767
```

- **+0.0042**：初盘到收盘之间市场获得的信息（首发、伤停、临场资金）
- **+0.0167**：市场开盘时就知道、我们不知道的，外加建模误差（用现有数据分不开）

于是 0.0209 被拆成：**约 0.004 的信息差 + 约 0.017 的能力差。**

这也解释了前四个实验为什么全都没用：它们都在爬那 0.017，而那一截不是"再加一个公开特征"能翻的。

## 六、六条工程教训

**1. 评估协议比模型重要。** 同类项目 90% 死在切分、泄漏和缺基准上，不在算法上。

**2. 用测试集调参是最隐蔽的作弊。** 我的梯度提升树最初 log loss 是 **1.21**——比常数基线还差。原因是我在 9 个测试赛季上试了 15 组超参数。改到 2017-18（测试集之前）上选，才回到 0.99。

**3. 有些东西样本量不足时根本估不出来。** 380 场估不出三个模型的堆叠权重：等权 0.9770，调权 0.9767–0.9803，全在噪声里。最后固定用"向等权收缩 50%"，而不是从 15 个格子里挑最好看的那个。

**4. 失败必须写进 README。** 五个实验四个负结果。负结果自带说服力：一个愿意公布"我试过、没用"的项目，它的"有用"才可信。

**5. 脏活比建模久。** 队名映射、赔率去抽水、列名变更（Pinnacle 从 `PS*` 改成 `PP*`）、时区——赛程是英国当地时间，我一开始拿它和机器时钟直接比较，在 UTC+8 的机器上把整轮比赛判成了"已开赛"。

**6. 自动化要能容忍局部失败。** 每周任务里，抓伤停数据那一步设了 `continue-on-error`：它挂了只影响未来的实验，不该让整次刷新失败。
