# 0.021：一个英超预测项目的五场失败

> 这是一篇待发布的长文草稿。所有数字都来自仓库里可复现的回测，配图在 `reports/`。
> 仓库：[github.com/haohaohao-cell/pythia-pl](https://github.com/haohaohao-cell/pythia-pl)

在 GitHub 上搜"英超预测"，你会看到一堆 README 写着"准确率 62%"。我做过一个，后来把它删了。
因为我发现，那些数字绝大多数是三类错误的产物：随机切分造成的数据泄漏、把赛后数据当赛前特征、
以及从来不和博彩公司比。

于是我重做了一个。规则只有一条：**只和博彩公司的收盘赔率比，并且把输多少算清楚。**

结果是 **0.0209**（log loss，越低越好）。然后我做了五个实验去追这个差距，五个全"失败"了。
但这五个失败拼出了一个比"我们输了"精确得多的答案。

---

## 一、先搭一个不会骗自己的框架

### 数据

13 个赛季、4,630 场英超，来自 football-data.co.uk：比分、射门、射正、红黄牌，
以及多家博彩公司的**初盘和收盘盘**。

最后两列是关键。赔率不是给球迷看的，是市场用真金白银投出来的概率。它是我能找到的最强的考官。

### 模型

四个，从简单到复杂：

| 模型 | 大白话 |
| --- | --- |
| 常数基线 | 永远报 43% / 24% / 33% |
| Elo + 逻辑回归 | 围棋段位式的评分，分差映射成概率 |
| Dixon-Coles | 每队拆成"进攻力/防守力"，用泊松分布掷出比分 |
| 梯度提升树 | 几百棵小决策树互相纠错 |

任何跑不赢常数基线的模型都是噪声——这条规则后来救了我一次。

### 评估协议

这三个决定比模型本身重要：

1. **walk-forward**：预测 2023-24 赛季时，只准用 2023-24 开赛前的数据。像真的穿越回去。
2. **log loss**：你说 90% 会发生、结果没发生，罚得很重；说 45%，罚得轻。它同时惩罚"错"和"假装确定"，墙头草和莽夫都拿不了高分。
3. **基准是收盘价**：不是和自己比，和别人比。

还有一条工程纪律：两个测试专门验证"把未来数据删掉，过去的特征一个数都不许变"。
其中一个测试还会**篡改未来的比赛结果**，确认过去那一行的特征纹丝不动。

### 结果

| 模型 | log loss | 准确率 |
| --- | --- | --- |
| 收盘价（去抽水） | **0.9558** | 55.0% |
| 融合模型 | 0.9767 | 53.0% |
| Elo + 逻辑回归 | 0.9788 | 53.4% |
| 梯度提升树 | 0.9911 | 52.0% |
| Dixon-Coles | 0.9941 | 51.4% |
| 常数基线 | 1.0686 | 43.7% |

差距 `+0.0209`，配对 bootstrap 的 95% 区间 `[+0.0147, +0.0271]`，不含 0。

**模型输给市场，而且不是运气。**

## 二、五个实验

### 实验一：温度校准 —— 你是不是过度自信？

这是这类模型最常见的辩护：也许它只是"太自信"了，校准一下就能打平。

做法：给每个模型加一个温度参数 `T`（`pᵢ → pᵢ^(1/T)` 归一化），在**上一季**的样本外预测上拟合，
绝不碰被测赛季。

| 模型 | log loss | + 温度 | 变化 | T 中位数 |
| --- | --- | --- | --- | --- |
| 融合 | 0.9767 | 0.9798 | +0.0031 | 1.00 |
| Elo | 0.9788 | 0.9805 | +0.0017 | 1.00 |
| Dixon-Coles | 0.9941 | 1.0030 | +0.0089 | 1.03 |
| 梯度提升 | 0.9911 | 0.9906 | **−0.0006** | 1.14 |

融合模型的 `T` 稳在 1.00——它本来就没病。唯一真过度自信的是梯度提升树（1.14，校准后确实降了 0.0006），
但它的绝对水平太差，救不回来。

更关键的证据在 Brier 分解里：

| | 可靠性↓ | 分辨率↑ | Brier |
| --- | --- | --- | --- |
| 收盘价 | 0.0012 | **0.0786** | 0.5681 |
| 融合模型 | 0.0016 | **0.0661** | 0.5811 |

**两家的可靠性几乎一样，差距全在分辨率。**

翻译成人话：模型不是不会报概率，是**知道得更少**。

### 实验二：xG —— 是不是少了个关键特征？

射正是"创造机会"的粗糙代理，xG 才是正主。接 Understat，13 季 4,635 场，覆盖率 100%
（顺便踩了个坑：Understat 的赛季 ID 不是起始年，2020 和 2021 都指向 2020-21，得用开球日期反推）。

严格消融：训练窗口、测试比赛、超参数全同，唯一变量是树模型有没有看到 xG 块。

| 变体 | log loss | 变化 |
| --- | --- | --- |
| 梯度提升（无 xG） | 0.9911 | — |
| 梯度提升 + xG | 0.9896 | −0.0015 |
| 等权融合（无 xG） | 0.9770 | — |
| 等权融合 + xG | 0.9756 | **−0.0014** |

配对 bootstrap：`−0.0014`，95% CI `[−0.0029, +0.0000]`，P(更好) = 0.97。

方向对，**但区间上界正好压在 0 上**。9 个赛季里 6 个改善，可 2021-22 一季就贡献了 −0.0058，
另外三季反而变差。

结论：有效，但薄到不值得为它每周依赖一个会被 Cloudflare 拦的抓取器。
xG 留作可选依赖，**不进主模型**。

### 实验三：伤停 —— 能不能拿到市场独享的信息？

既然差的是信息，那就去拿阵容。FPL 官方 API 的 `bootstrap-static` 看起来完美：
669 名球员的实时状态（`a` 可用 / `d` 存疑 / `i` 伤停 / `s` 停赛 / `u` 不可用），
本轮 200 人不完全可用。

然后我问了一个致命的问题：**能回测吗？**

不能。查单球员的 `element-summary/{id}`，逐轮历史的字段是：

```
minutes, starts, total_points, expected_goals, expected_assists, ...
```

**全是赛后才知道的东西，没有一个字段记录"那一轮赛前他是不是伤停"。**

API 只暴露"现在"，不暴露"当时"。没有历史快照，就没有样本外；用今天的伤停去解释过去的比赛，就是穿越。

所以这件事失败的原因不是技术，是**因果顺序**。

能做的是从今天开始攒：每次刷新存一个 20 行的球队级快照（按赛季分钟加权），提交进仓库。
一年后就有 50 多个时间点，这个问题才第一次变得可回答。

顺带验证了一句老话：FPL 的队名又是另一套写法（`Spurs`、`Hull City`、`Ipswich Town`、`Coventry City`）。
**这是第三个供应商的第三套拼写**——"60% 的工作量在队名映射上"这个说法，我已经验证三次了。

### 实验四：大小球 —— 结构模型的主场？

前面全在 1X2 上。但 Dixon-Coles 产出的是完整比分分布，它天然能定价"总进球数"，
而任何基于 1X2 标签的分类器都不能。这本来应该是它的主场。

| | log loss |
| --- | --- |
| Dixon-Coles | 0.6871 |
| 收盘价 | **0.6738** |
| 常数基准 | 0.6894 |

对庄家 `+0.0134`（95% CI `+0.0064 ~ +0.0205`）。

**但真正扎心的是第三行**：模型只比"每个赛季都报同一个大球率"好 **0.0023**，
而庄家比常数好 **0.0156**。

庄家在大球上有真实的分辨力，我们几乎只有水平。

2023-24 是最惨的一季：实际大球率 64.7%，模型只给 48.3%（庄家 58.6%）。
我试过按赛季进球水平缩放，那一季从 0.7133 降到 0.6890，但其他赛季被拖累，净效应在噪声内。

结论：**比分分布对"谁赢"够用，对"进几个"不够。**

### 实验五：盘口先验 —— 到底能补回多少？

最后一个问题：既然公开特征补不上，那把**盘口本身当特征**呢？

模型概率与去抽水**初盘**按权重混合（收盘是裁判，不能用；初盘是开赛前几小时的合法信息），
权重在历史赛季上调。

| | log loss |
| --- | --- |
| 模型 | 0.9767 |
| 初盘 | 0.9601 |
| 混合（调优） | 0.9608 |
| 收盘 | **0.9558** |

**优化器把权重推到了 1.00。**

九季里六季完全是 1.00，其余是 0.85 / 0.95 / 0.5（首季无历史）。
也就是说：**一旦手里有盘口，这个模型就是一个噪声项，最优用法是扔掉。**

所以"补回 76%"这个数字要读准：**是初盘自己补的，不是模型补的。**

![盘口梯子](../reports/prior_ladder.png)

真正有价值的是这条梯子：

```
收盘 0.9558  ──+0.0042──▶  初盘 0.9601  ──+0.0167──▶  模型 0.9767
```

- **+0.0042**：从初盘到收盘之间市场获得的信息——首发、伤停、临场资金。
- **+0.0167**：市场开盘时就已消化、而我们没有的信息，外加我们的建模误差（用现有数据，两者分不开）。

## 三、所以那个 0.021 到底是什么

> **约 0.004 是"赛前信息差"，约 0.017 是"公开数据与建模能力的差距"。**

这句话解释了前面四个实验为什么全都没用：它们都在试图翻越那 0.017，
而那一截不是"再加一个公开特征"能翻的。

它也解释了博彩市场为什么是有效的——不是因为庄家会算命，而是因为
**它在开赛前一小时就知道谁今天不能上，而你要到比赛结束才知道。**

## 四、方法上的五个教训（也许比结论更有用）

**1. 评估协议比模型重要。**
同类项目 90% 死在随机 KFold、赛后特征和缺基准上，不在算法上。
"准确率 62%"这个数字，只要用随机切分就能轻易做出来。

**2. 用测试集调参是最隐蔽的作弊。**
我的梯度提升树最初 log loss 是 1.21——**比常数基线还差**。原因是我在 9 个测试赛季上试了 15 组超参数。
后来改到 2017-18（测试集之前的赛季）上选，才回到 0.99。
这个坑值得单独写一篇。

**3. 有些东西在样本量不足时根本估不出来。**
380 场比赛估不出三个模型的堆叠权重：等权 0.9770，调权 0.9767～0.9803，全在噪声里。
所以我固定用"向等权收缩 50%"，而不是从 15 个格子里挑最好看的那个。

**4. 失败必须写进 README。**
五个实验，四个是负结果。如果只写赢的那部分，下次还会踩同样的坑。
而且负结果自带说服力：一个愿意公布"我试过、没用"的项目，它的"有用"才可信。

**5. 脏活比建模久。**
队名映射（三家供应商三套写法）、赔率去抽水、时区（赛程是英国当地时间，我一开始用机器时钟比较，
在 UTC+8 的机器上把整轮比赛判成了"已开赛"）、列名变更（Pinnacle 从 `PS*` 改成 `PP*`）……
