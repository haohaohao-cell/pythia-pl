我做了个英超预测模型，然后花了四周证明它没用


先给结论：我这个模型的 log loss 是 0.9767，博彩公司的收盘赔率是 0.9558。差 0.0209。

这不是"模型太烂"的问题。我用四个实验去追这 0.0209，四个全失败了——而这四个失败拼出了一个比"我输了"精确得多的答案：

这 0.0209 里，大约 0.004 是「赛前信息差」，0.017 是「公开数据和建模能力的差距」。

下面把整个过程摊开讲。所有数字都能在仓库里复现。


一、我为什么不信"准确率 62%"

在 GitHub 上搜"英超预测"，你会看到一堆 README 写着"准确率 62%"。我自己也写过一个，后来删了。

因为我发现，那些数字绝大多数是三类错误的产物：

第一，随机切分造成的数据泄漏。用 KFold 切比赛数据，训练集里混进了"未来"的比赛，模型等于提前看了答案。

第二，把赛后数据当赛前特征。比如拿"本赛季场均 xG"当特征——那个数只有打完才知道。

第三，从来不和博彩公司比。

第三条最致命。你在一个没有对手的考场上考 62 分，不代表你会踢球。博彩公司的收盘赔率，是全世界最会预测足球的一群人用真金白银投出来的概率，它是现成的、免费的、每天更新的标准答案。不比它，等于自娱自乐。

所以我给自己立了三条规矩：只和收盘赔率比；用 walk-forward 不用随机切分；主指标用 log loss 不用准确率。


二、先把尺子立起来

数据是 13 个赛季、4,630 场英超，来自 football-data.co.uk。每场一行：比分、射门、射正、红黄牌，以及多家博彩公司的初盘和收盘盘。

模型四个，从简单到复杂：

常数基线：永远报 43% / 24% / 33%。
Elo + 逻辑回归：围棋段位式的评分，两队分差映射成概率。
Dixon-Coles：每支球队拆成"进攻力"和"防守力"两个数，算出期望进球，再用泊松分布掷出比分。
梯度提升树：几百棵小决策树互相纠错。

最后再按前两季的战绩给后三个加权融合。

评估协议有三个关键决定，它们比模型本身重要得多：

一是 walk-forward。预测 2023-24 赛季时，只准用 2023-24 开赛前的数据。像真的穿越回去，而不是事后诸葛亮。

二是 log loss。你说 90% 会发生、结果没发生，罚得很重；说 45%，罚得轻。它同时惩罚"错"和"假装确定"，所以墙头草和莽夫都拿不了高分。

三是基准必须是收盘价。不是和自己比，是跟对手比。

另外还有一条工程纪律：两个自动化测试专门验证"把未来数据删掉，过去的特征一个数都不许变"。其中一个测试还会故意篡改未来的比赛结果，确认过去那一行的特征纹丝不动。

这样跑出来的结果是这样：

收盘价 0.9558
融合模型 0.9767
Elo + 逻辑回归 0.9788
梯度提升树 0.9911
Dixon-Coles 0.9941
常数基线 1.0686

按准确率看：收盘价 55.0%，模型 53.0%。

差距 +0.0209，配对 bootstrap 的 95% 区间是 [+0.0147, +0.0271]，不含 0。

模型输给市场，而且不是运气。

【图 1：模型 vs 收盘价】

把累计曲线画出来看更直观：前 500 场抖得厉害（样本小），900 场之后排名稳定下来，然后就再也没交叉过——市场那条线一直在最上面。

【图 2：累计 log loss】

到这里，一个诚实的项目该做的事情已经做完了：报个数字，收工。但我不甘心——这 0.02 到底是差在哪？于是我做了五个实验。


三、五个实验，五个失败

实验一：温度校准——你是不是过度自信？

这是这类模型最常见的辩护：也许它只是太自信了，校准一下就能打平。

做法是给每个模型加一个温度参数 T，把概率 p 变成 p 的 1/T 次方再归一化，在上一季的样本外预测上拟合，绝不碰被测赛季。

结果是：融合模型的 T 稳在 1.00，校准后反而变差 0.0031。唯一真过度自信的是梯度提升树，T 是 1.14，校准后确实降了 0.0006——但它的绝对水平太差，救不回来。

更关键的证据在一张分解表上。Brier 分数可以拆成"可靠性"和"分辨率"两部分：

收盘价的可靠性 0.0012，模型 0.0016。几乎一样。
收盘价的分辨率 0.0786，模型 0.0661。差了一大截。

翻译成人话：模型不是不会报概率，是知道得更少。


实验二：xG——是不是少了个关键特征？

射正是"创造机会"的粗糙代理，xG 才是正主。我接了 Understat 的数据，13 个赛季、4,635 场，覆盖率 100%。

顺手踩了个坑：Understat 的赛季 ID 不是起始年，2020 和 2021 都指向 2020-21，得用开球日期反推才能对上。

然后做了严格消融：训练窗口、测试比赛、超参数全部相同，唯一的变量是树模型有没有看到 xG。

梯度提升树：0.9911 → 0.9896，好 0.0015。
等权融合：0.9770 → 0.9756，好 0.0014。

配对 bootstrap 的 95% 区间是 [−0.0029, +0.0000]——上界正好压在 0 上。9 个赛季里 6 个改善，但 2021-22 一季就贡献了 −0.0058，另外三季反而变差。

方向对，但薄到不值得为它每周依赖一个会被 Cloudflare 拦的抓取器。所以 xG 留作可选依赖，不进主模型。


实验三：伤停——能不能拿到市场独有的信息？

既然差的是信息，那就去拿阵容。FPL 官方 API 的 bootstrap-static 看起来完美：669 名球员的实时状态，a 是可出场、d 是存疑、i 是伤停、s 是停赛、u 是不可用，还带一个 "Knee injury, expected back 15 Nov" 的说明。这一轮 669 人里有 200 人不完全可用。

然后我问了一个致命的问题：能回测吗？

不能。查单个球员的 element-summary 接口，逐轮历史的字段是 minutes、starts、total_points、expected_goals……全是赛后才知道的东西。没有任何一个字段记录"那一轮赛前他是不是伤停"。

API 只暴露"现在"，不暴露"当时"。没有历史快照，就没有样本外；用今天的伤停名单去解释过去的比赛，就是穿越。

所以这件事失败的原因不是技术，是因果顺序。

能做的只剩一件：从今天开始攒。每次刷新存一个 20 行的球队级快照，按赛季分钟加权，提交进仓库。一年后就有 50 多个时间点，这个问题才第一次变得可回答。

顺带验证了一句老话：FPL 的队名又是另一套写法——Spurs、Hull City、Ipswich Town、Coventry City。这是第三个数据源的第三套拼写。所谓"60% 的工作量在队名映射上"，我已经验证三次了。


实验四：大小球——结构模型的主场？

前面全在 1X2 上。但 Dixon-Coles 产出的是完整比分分布，它天然能定价"总进球数"，而任何基于 1X2 标签的分类器都不能。这本来应该是它的主场。

数据上有个门槛：football-data 从 2019-20 才开始有大小球赔率，所以这是 7 个赛季、2,729 场。

Dixon-Coles 0.6871，收盘价 0.6738，常数基准 0.6894。

对庄家 +0.0134。

但真正扎心的是第三行：模型只比"每个赛季都报同一个大球率"好 0.0023，而庄家比常数好 0.0156。

庄家在大球上有真实的分辨力，我们几乎只有水平。

2023-24 是最惨的一季：实际大球率 64.7%，模型只给 48.3%，庄家给 58.6%。我试过按赛季进球水平缩放，那一季从 0.7133 降到 0.6890，但其他赛季被拖累，净效应在噪声内。

结论：比分分布对"谁赢"够用，对"进几个"不够。

实验五：盘口先验——到底能补回多少？

最后一个问题：既然公开特征补不上，那把盘口本身当特征呢？

做法是把模型概率和去抽水后的初盘按权重混合——注意用初盘不用收盘，收盘是我的裁判，不能既当运动员又当裁判。权重在历史赛季上调。

模型 0.9767
初盘 0.9601
混合（调优） 0.9608
收盘 0.9558

优化器把权重推到了 1.00。

九季里六季完全是 1.00，其余是 0.85、0.95、0.5（首季无历史）。也就是说：一旦手里有盘口，这个模型就是一个噪声项，最优用法是扔掉。

所以"补回 76%"这个数字要读准——是初盘自己补的，不是模型补的。


四、所以那 0.0209 到底是什么

真正有价值的是这条梯子：

收盘 0.9558  ──+0.0042──▶  初盘 0.9601  ──+0.0167──▶  模型 0.9767

第一段 +0.0042：从初盘到收盘之间市场获得的信息——首发、伤停、临场资金。

第二段 +0.0167：市场开盘时就已消化、而我们没有的信息，外加我们的建模误差。这两者用现有数据分不开。

于是那个 0.0209 有了精确的解剖：

约 0.004 是「赛前信息差」，约 0.017 是「公开数据与建模能力的差距」。

这也一次性解释了前面四个实验为什么全都没用：它们都在试图翻越那 0.017，而那一截不是"再加一个公开特征"能翻的。

它也解释了博彩市场为什么是有效的——不是因为庄家会算命，而是因为它在开赛前一小时就知道谁今天不能上，而你要到比赛结束才知道。

五、五个方法论教训

1. 评估协议比模型重要。

同类项目 90% 死在随机 KFold、赛后特征和缺基准上，不在算法上。"准确率 62%"这个数字，只要用随机切分就能轻易做出来。

2. 用测试集调参是最隐蔽的作弊。

我的梯度提升树最初 log loss 是 1.21——比常数基线还差。原因是我在 9 个测试赛季上试了 15 组超参数。后来改到 2017-18（测试集之前的赛季）上选，才回到 0.99。这个坑值得单独写一篇。

3. 有些东西在样本量不足时根本估不出来。

380 场比赛估不出三个模型的堆叠权重：等权 0.9770，调权 0.9767 到 0.9803，全在噪声里。所以最后固定用"向等权收缩 50%"，而不是从 15 个格子里挑最好看的那个。

4. 失败必须写进 README。

五个实验，四个是负结果。如果只写赢的那部分，下次还会踩同样的坑。而且负结果自带说服力：一个愿意公布"我试过、没用"的项目，它的"有用"才可信。

5. 脏活比建模久。

队名映射（三家数据源三套写法）、赔率去抽水、列名变更（Pinnacle 从 PS 改成 PP）、时区——赛程是英国当地时间，我一开始拿它和机器时钟直接比较，在我的 UTC+8 电脑上把整轮比赛判成了"已开赛"。

最后说一句。

这个项目最有价值的产出，不是那个 0.9767，而是"证明它不能盈利"的完整过程。我没能做出一个比博彩公司更准的模型，但我知道自己差在哪、差多少、以及为什么——这个答案比一个虚高的准确率值钱得多。
